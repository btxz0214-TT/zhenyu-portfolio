## 1. 核心判断

目前的经历较有力地证明了金融建模、Python 工程交付和个人资金实盘交易，但对独立发现并验证 alpha 的呈现不足。这个差异对纯 QR 最明显，不能直接推广为所有 QD / Trader 岗位都不适合。

过去的简历优化较强调商业价值、AI 使用、数量和页面利用率。下一轮应更多呈现：具体问题 → 数学或工程方法 → 验证设计 → 结果。量化数字多，不等于量化研究证据充分。

研究参考包括 Job 工作区中的 Finstock QR 与 Jane Street HK Trader 简历。它们与本 repo 的 Citi 简历不是同一个版本，不能互相覆盖全部内容。

“需要提炼”不等于没做过。先查既有项目记录，不凭简历缺少文字就断定缺少经验。

三种岗位应分别组织主线：

- QR：提出问题、检验假设、解释结果。实验次数不是有效 alpha 的证据。
- QD：把金融问题实现为准确、高效、可靠的计算系统。现有 ALM 工作是重要优势。
- Trader：识别价格机会、管理敞口并执行。账户总收益不能自动归因于某一个策略。

## 6. 给修改 ALM 内容的 agent 的具体任务

### 先读取

1. 本报告与仓库 README。
2. `calculation-engine.html`、相关 `data.js` / `app.js`，理解现有案例和交互。
3. `resumes/Zhenyu_Xiao_Citi_AI_Engineer_Resume.md`，注意这仍是 AI 岗的版本。
4. 用户提供的实际 ALM 研究/开发材料；本公开 repo 不包含内部引擎源码。没有访问权限时不要假装审计过代码。
5. 若修改 Job 工作区里的正式简历，读取该工作区 `AGENTS.md` 和对应 JD；不能只凭本 repo 的 Citi Markdown 覆盖所有岗位。

### 需要提炼的三个证据链

**建模：**一个具体模型差异 → 用户识别的金融机制 → 实现变化 → 对账结果 → 回归覆盖。

**性能：**原始瓶颈 → 用户选择的计算方案 → 同等工作负载下的时间变化 → 结果一致性检查。区分厂商与自研端到端对比、同一自研实现内部优化；不能把 8h→2h 全部归因给一个未隔离测量的优化。

**验证：**对照指标与粒度 → 六个快照/场景覆盖 → 相对与绝对容差 → 异常诊断。把验证写成模型检验设计，而不是普通数据检查。

### 修改优先级

1. 先增加一个证据完整的建模案例；其次增强性能优化和验证方法。
2. Python、金融模型、数值计算和个人贡献置于普通 QR/QD 版本前部。
3. 保留 AI-agent 使用，但解释用户负责的规格、金融规则、验收和 review；Citi 等 AI 岗仍可给予 orchestration 更多篇幅。
4. 保留潜在 $1M+ 商业价值，不将其作为研究能力的唯一证明。
5. 保留 ALM Engine / ALM Analytics 两个项目块。避免同一成果重复占据两块。
6. 公开网站可以比一页简历多解释一层：问题、模型设计、验证、性能。不要贴内部数据或专有源码。

### 可用的写作骨架（不是新增事实）

只有括号内容得到项目证据支持后才完成句子；不能把占位符带进投递版本。

- 建模：Resolved [specific modeling discrepancy] by [financial/mathematical correction], reducing [defined error] from [baseline] to [result] across [validated scope].
- 性能：Implemented [verified computational method] for [workload], reducing runtime from [before] to [after] while preserving [defined numerical agreement].
- 验证：Designed [comparison/regression approach] across [snapshots and contract scope], using [documented tolerance treatment] to establish [measured agreement].

不要求每条都采用同一句式，也不硬加统计模型、Monte Carlo、优化算法、Greeks 或其他尚未确认的方法。

## 7. 交付要求

- 先做 evidence-to-claim 对照，再改文字；只报告有来源的数字。
- 申请材料强调优势，不加入无关的缺陷清单。本文中的证据边界是 agent 工作要求，不必搬到简历正文。
- 简历保持既定一页样式、字号、项目结构和页面利用率。不要靠缩字或不相关内容填满。
- 正式简历修改须按 Job 工作区约定同步原 Google Doc、PDF 和本地源文件；本 repo 的 Markdown 不是这些交付的替代品。
- 只更新用户要求的内容。研究报告发布不等于授权修改计算引擎逻辑、改变业绩数据或自动部署网站。
- 最终说明改了什么、依据是什么、哪些待核查素材没有采用。

建议从第 5 节的提前还款案例开始，然后研究性能与数值一致性。目标是让已有建模贡献更清楚，而不是把 ALM 工作重新命名为未经证明的 alpha research。
